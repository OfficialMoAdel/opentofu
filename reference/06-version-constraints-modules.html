🔒 قيود الإصدارات (Version Constraints)

بدون قيود الإصدارات، يقوم tofu init بتنزيل أحدث إصدار من الـ Provider. هذا قد يسبب مشاكل إذا تغيرت الوظائف بين الإصدارات.

📄 تحديد إصدار معين

terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "2.3.0"  # ← إصدار محدد بالضبط
    }
  }
}

📄 عوامل المقارنة (Comparison Operators)

العامل الاسم المعنى مثال
= يساوي إصدار محدد بالضبط version = "2.3.0"
!= لا يساوي استبعاد إصدار معين version = "!= 2.4.1"
> أكبر من إصدارات أحدث فقط version = "> 2.3.0"
< أصغر من إصدارات أقدم فقط version = "< 2.4.1"
>= أكبر أو يساوي من هذا الإصدار فما فوق version = ">= 2.3.0"
<= أصغر أو يساوي حتى هذا الإصدار version = "<= 2.4.1"
~> Pessimistic إصدارات ترقيعية فقط version = "~> 2.2.0"

⚠️ تنبيه مهم

العامل == (يساوي مع علامتين) غير صالح في OpenTofu! استخدم = (علامة واحدة) فقط.

📄 الجمع بين العوامل

# نطاق محدد: أكبر من 2.2.3 وأصغر من 2.4.1 وليس 2.4.0
version = "> 2.2.3, != 2.4.0, < 2.4.1"
# النتيجة: سيتم تنزيل 2.3.0

📄 عامل التشاؤم (Pessimistic Constraint) ~>

يسمح بتنزيل الإصدار المحدد وأي إصدارات ترقيعية لاحقة، لكن ليس الإصدارات الرئيسية الجديدة. 

# مثال 1: يسمح بـ 2.2.0, 2.2.1, 2.2.3, 2.3.0, ... حتى 2.4.1
version = "~> 2.2"

# مثال 2: يسمح بـ 2.2.0, 2.2.1, 2.2.3 فقط (ليس 2.3.0)
version = "~> 2.2.0"

💡 الفرق بين ~> 2.2 و ~> 2.2.0

  • ~> 2.2: يسمح بأي إصدار من 2.2 إلى أقل من 3.0 (يشمل 2.3, 2.4, إلخ)
  • ~> 2.2.0: يسمح فقط بإصدارات الترقيع من 2.2.x (لا يشمل 2.3)

📄 مثال عملي كامل من الملف

terraform {
  required_providers {
    k8s = {
      source  = "hashicorp/kubernetes"
      version = "> 1.12.0, != 1.13.1, < 1.13.3"
      # النتيجة: سيتم تنزيل 1.13.2
    }
    helm = {
      source  = "hashicorp/helm"
      version = "~> 1.2.0"
      # النتيجة: سيتم تنزيل 1.2.4 (أحدث ترقيع)
    }
  }
}

📁 الوحدات (Modules) - الأساسيات

كل مجلد يحتوي على ملفات إعدادات OpenTofu هو وحدة. الوحدات تتيح إعادة استخدام الإعدادات وتبسيط الكود.

📂 أنواع الوحدات

Root Module

مجلد العمل الحالي الذي تعمل منه

←
Child Module

وحدة يتم استدعاؤها من الـ Root

📄 الـ module block

module "<module_name>" {
  source = "<path_to_module>"  # ← مطلوب دائماً
  # arguments إضافية
}

💡 لماذا نستخدم الوحدات؟

  • تبسيط الإعدادات: بدلاً من آلاف الأسطر، ملفات قصيرة وسهلة
  • إعادة الاستخدام: نفس الوحدة لعدة بيئات (dev, staging, prod)
  • تقليل الأخطاء: وحدة مختبرة ومعتمدة
  • تقييد الإعدادات: يمكن إخفاء بعض المتغيرات عن المستخدم

🏠 الوحدات المحلية (Local Modules)

وحدات موجودة على نفس الجهاز الذي تعمل عليه. يتم الإشارة إليها عبر مسار نسبي أو مطلق.

📂 هيكل المجلدات

/root/opentofu-projects/ ├── modules/ │ └── payroll-app/ ← Child Module │ ├── app_server.tf │ ├── dynamodb_table.tf │ ├── s3_bucket.tf │ └── variables.tf ├── us-payroll-app/ ← Root Module │ ├── main.tf │ └── provider.tf └── uk-payroll-app/ ← Root Module ├── main.tf └── provider.tf

📄 مثال: وحدة الـ Payroll App

# /root/opentofu-projects/modules/payroll-app/variables.tf
variable "app_region" {
  type = string
}

variable "ami" {
  type = string
}

variable "bucket" {
  default = "flexit-payroll-alpha-22001c"
}
# /root/opentofu-projects/us-payroll-app/main.tf
module "us_payroll" {
  source     = "../modules/payroll-app"  # ← مسار نسبي
  app_region = "us-east-1"
  ami        = "ami-2357552336avm"
}

# /root/opentofu-projects/uk-payroll-app/main.tf
module "uk_payroll" {
  source     = "../modules/payroll-app"
  app_region = "eu-west-2"
  ami        = "ami-35e140119877avm"
}

🔍 الـ Addressing Syntax للوحدات

# الصيغة العامة
module.module_name.resource_type.resource_name

# مثال عملي
module.us_payroll.aws_dynamodb_table.payroll_db

🌐 وحدات الـ Registry (Remote Modules)

وحدات عامة مخزنة في الـ OpenTofu/Terraform Registry. يمكن استخدامها مباشرة دون تنزيلها يدوياً.

📄 مثال: Security Group من الـ Registry

module "ssh_security_group" {
  source  = "terraform-aws-modules/security-group/aws//modules/ssh"
  version = "~> 5.0"

  # Arguments المطلوبة
  name              = "ssh-access"
  vpc_id            = "vpc-7d8d215"
  ingress_cidr_blocks = ["10.10.0.0/16"]
}

📄 مثال: IAM User من الـ Registry

module "iam_iam-user" {
  source  = "terraform-aws-modules/iam/aws//modules/iam-user"
  version = "5.28.0"

  # Argument المطلوب الوحيد
  name = "max"

  # تعطيل الموارد الإضافية
  create_iam_access_key         = false
  create_iam_user_login_profile = false
}

⚠️ حدد دائماً إصدار الوحدة!

إذا لم تحدد version، سيتم تنزيل أحدث إصدار. هذا قد يكسر إعداداتك إذا تغيرت الوحدة. 

# ❌ خطر - قد يتغير الإصدار
version = "~> 5.0"  # مرن جداً

# ✅ أفضل - إصدار محدد
version = "5.28.0"  # ثابت

🔧 تنزيل الوحدات

# تنزيل الـ modules فقط (بدون الـ providers)
tofu get

# أو مع الـ providers
tofu init

⚖️ مقارنة: الوحدات المحلية مقابل البعيدة

المعيار الوحدات المحلية وحدات الـ Registry
الموقع على جهازك على الـ Registry العام
الـ source "../modules/my-module" "terraform-aws-modules/..."
الـ version غير مطلوب مستحسن جداً
التحكم كامل - يمكنك التعديل محدود - كما هي
المشاركة صعبة (تحتاج نسخ الملفات) سهلة (عبر الـ Registry)
متى تستخدمها؟ إعدادات خاصة بمؤسستك حلول عامة ومعتمدة

🎯 مثال عملي كامل: نشر نفس التطبيق في بيئات متعددة

📂 الخطوة 1: إنشاء الوحدة

# /root/opentofu-projects/modules/payroll-app/app_server.tf
resource "aws_instance" "app_server" {
  ami           = var.ami
  instance_type = "t2.medium"  # ← ثابت في الوحدة
  tags = {
    Name = "${var.app_region}-app-server"
  }
  depends_on = [
    aws_dynamodb_table.payroll_db,
    aws_s3_bucket.payroll_data
  ]
}

# /root/opentofu-projects/modules/payroll-app/s3_bucket.tf
resource "aws_s3_bucket" "payroll_data" {
  bucket = "${var.app_region}-${var.bucket}"
}

# /root/opentofu-projects/modules/payroll-app/dynamodb_table.tf
resource "aws_dynamodb_table" "payroll_db" {
  name         = "user_data"  # ← ثابت في الوحدة
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "EmployeeID"
}

📂 الخطوة 2: استخدام الوحدة في بيئات مختلفة

# /root/opentofu-projects/us-payroll-app/main.tf
module "us_payroll" {
  source     = "../modules/payroll-app"
  app_region = "us-east-1"
  ami        = "ami-2357552336avm"
}

# /root/opentofu-projects/uk-payroll-app/main.tf
module "uk_payroll" {
  source     = "../modules/payroll-app"
  app_region = "eu-west-2"
  ami        = "ami-35e140119877avm"
}

✅ النتيجة

  • نفس البنية التحتية في منطقتين مختلفتين
  • قيم ثابتة في الوحدة (instance_type, DynamoDB name)
  • قيم متغيرة من الـ Root (region, AMI)
  • كود نظيف وقابل للصيانة

⚠️ أخطاء شائعة يجب تجنبها

❌ خطأ 1: عدم تحديد إصدار الـ Provider

بدون version، قد يتم تنزيل إصدار جديد يكسر إعداداتك.

❌ خطأ 2: استخدام == بدلاً من =

# ❌ خطأ - عامل غير صالح
version = "== 2.3.0"

# ✅ صحيح
version = "2.3.0"

❌ خطأ 3: عدم تحديد إصدار الوحدة البعيدة

الوحدات البعيدة تتغير باستمرار. حدد دائماً version لتجنب المفاجآت.

❌ خطأ 4: نسيان tofu init بعد إضافة وحدة

بعد إضافة وحدة جديدة، يجب تشغيل tofu init لتنزيلها.

🎤 أسئلة مقابلات مهمة

سؤال 1: لماذا نستخدم قيود الإصدارات؟

لأن وظائف الـ Provider قد تتغير بشكل جذري بين الإصدارات. قيود الإصدارات تضمن أن إعداداتك ستعمل كما هو متوقع، وتمنع التحديثات التلقائية التي قد تكسر البنية التحتية.

سؤال 2: ما الفرق بين ~> 2.2 و ~> 2.2.0؟

~> 2.2: يسمح بأي إصدار من 2.2 حتى أقل من 3.0 (يشمل 2.3, 2.4).
~> 2.2.0: يسمح فقط بإصدارات الترقيع 2.2.x (لا يشمل 2.3).

سؤال 3: ما الفرق بين Root Module و Child Module؟

Root Module: مجلد العمل الحالي الذي تعمل منه (حيث تشغل أوامر tofu).
Child Module: وحدة يتم استدعاؤها من الـ Root عبر الـ module block.

سؤال 4: متى تستخدم الوحدات المحلية ومتى تستخدم وحدات الـ Registry؟

المحلية: لإعدادات خاصة بمؤسستك أو مشاريعك.
الـ Registry: لحلول عامة ومعتمدة من المجتمع (مثل VPC, Security Groups).

سؤال 5: ما هي صيغة الـ Addressing للوحدات؟

module.module_name.resource_type.resource_name
مثال: module.us_payroll.aws_dynamodb_table.payroll_db
