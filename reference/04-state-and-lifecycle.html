مرجع شامل لمفهوم الحالة، قواعد دورة الحياة، وأوامر الحالة

📋 نظرة عامة (Overview)

الحالة (State) هي قلب عمل OpenTofu. بدونها، لا يمكن لـ OpenTofu معرفة ما تم إنشاؤه وما يجب تحديثه أو حذفه. قواعد دورة الحياة (Lifecycle Rules) تتحكم في كيفية إنشاء وحذف الموارد.

ℹ️ حقائق أساسية عن الحالة

  • الحالة إلزامية - لا يمكن تعطيلها
  • يمكن تعطيل تحديث الحالة عبر -refresh=false
  • الحالة بصيغة JSON
  • تُخزن محلياً افتراضياً، لكن يجب نقلها إلى Remote Backend

💾 ملف الحالة (State File)

عند أول tofu apply، يتم إنشاء ملف الحالة تلقائياً في نفس مجلد ملفات الإعداد.

📄 الملفات الناتجة

# ملف الحالة الرئيسي
terraform.tfstate

# النسخة الاحتياطية
terraform.tfstate.backup

🔍 محتوى ملف الحالة

ملف الحالة يحتوي على جميع تفاصيل البنية التحتية:

المحتوى الوصف
Resource IDs معرفات جميع الموارد المُنشأة
Provider Info معلومات الـ Provider المستخدم
Resource Attributes جميع سمات الموارد (IP, ARN, etc.)
Dependencies الاعتماديات بين الموارد

⚠️ تحذيرات مهمة جداً

  • لا تضع ملف الحالة في Git! يحتوي معلومات حساسة (كلمات مرور، مفاتيح)
  • لا تحرر ملف الحالة يدوياً! استخدم الأوامر المخصصة
  • استخدم Remote Backend مثل S3, Azure Blob, GCS

🔄 تحديث الحالة (State Refresh)

قبل كل plan أو apply، يقوم OpenTofu بتحديث الحالة لتتطابق مع الواقع.

🔧 تعطيل التحديث (لحالات خاصة)

# تعطيل تحديث الحالة (في البيئات الكبيرة فقط)
tofu apply -refresh=false

⚠️ متى تستخدم -refresh=false؟

فقط في البيئات الكبيرة جداً (آلاف الموارد) حيث يستغرق التحديث وقتاً طويلاً. لا تستخدمه بشكل روتيني لأنه قد يؤدي إلى عدم اتساق بين الحالة والواقع.

🔧 أمر التحديث اليدوي

# تحديث الحالة يدوياً (دون تعديل الموارد)
tofu refresh

💡 ما الفرق بين tofu refresh و tofu apply؟

tofu refresh فقط يحدث ملف الحالة ليتطابق مع الواقع، لكنه لا يعدل أي موارد. بينما tofu apply قد يعدل الموارد بناءً على الاختلافات.

🔄 قواعد دورة الحياة (Lifecycle Rules)

قواعد دورة الحياة تتحكم في كيفية إنشاء وحذف الموارد. تُضاف داخل الـ resource block باستخدام الـ lifecycle block.

create_before_destroy

يُنشئ المورد الجديد قبل حذف القديم. مفيد للـ Zero Downtime.

create_before_destroy = true

prevent_destroy

يمنع حذف المورد نهائياً، حتى لو تغيرت الإعدادات. مفيد لقواعد البيانات.

prevent_destroy = true

ignore_changes

يتجاهل تغييرات معينة في السمات. مفيد للتغييرات اليدوية.

ignore_changes = [tags]

1️⃣ create_before_destroy

resource "aws_instance" "webserver" {
  ami           = "ami-0edab43b6fa892279"
  instance_type = "t2.micro"

  lifecycle {
    create_before_destroy = true  # ← إنشاء الجديد قبل حذف القديم
  }
}
السلوك الافتراضي

حذف القديم ← إنشاء الجديد

VS
مع create_before_destroy

إنشاء الجديد ← حذف القديم

⚠️ تنبيه مهم

في بعض الحالات، قد لا يعمل هذا كما تتوقع. مثال: ملف محلي (local_file) لا يمكن أن يكون له نفس الاسم مرتين في نفس الوقت. في هذه الحالة، سيتم حذف الملف الجديد والقديم معاً!

2️⃣ prevent_destroy

resource "aws_instance" "database" {
  ami           = var.ami
  instance_type = "m5.large"

  lifecycle {
    prevent_destroy = true  # ← منع الحذف نهائياً
  }
}

💡 متى تستخدم prevent_destroy؟

  • قواعد البيانات (Databases)
  • الأنظمة الحرجة (Critical Systems)
  • الموارد التي لا يمكن إعادة إنشائها بسهولة

ملاحظة: لا يمنع tofu destroy من الحذف! يمنع فقط الحذف الناتج عن تغييرات في الإعدادات.

3️⃣ ignore_changes

resource "aws_instance" "webserver" {
  ami           = "ami-0edab43b6fa892279"
  instance_type = "t2.micro"
  tags = {
    Name = "webserver"
  }

  lifecycle {
    ignore_changes = [ tags ]  # ← تجاهل تغييرات الـ tags
  }
}
# تجاهل جميع التغييرات
lifecycle {
  ignore_changes = [ all ]  # ← تجاهل كل شيء
}

💡 متى تستخدم ignore_changes؟

عندما يتم تعديل المورد يدوياً أو بأدوات أخرى، ولا تريد من OpenTofu إعادة التغييرات إلى ما كانت عليه.

🛠️ أوامر الحالة (State Commands)

هذه الأوامر تستخدم لإدارة الحالة دون تحرير الملف يدوياً. استخدمها دائماً بدلاً من التحرير اليدوي.

الأمر الوظيفة مثال
tofu state list عرض جميع الموارد في الحالة tofu state list
tofu state show عرض سمات مورد محدد tofu state show local_file.pet
tofu state mv إعادة تسمية أو نقل مورد tofu state mv random_pet.old random_pet.new
tofu state rm إزالة مورد من الحالة (لا يحذفه فعلياً) tofu state rm local_file.pet
tofu state pull تنزيل الحالة البعيدة tofu state pull > backup.json
tofu state push رفع الحالة المحلية إلى البعيدة tofu state push backup.json

🔍 عرض الموارد في الحالة

# عرض جميع الموارد
tofu state list
# النتيجة:
# local_file.pet
# aws_instance.webserver

# عرض مورد محدد
tofu state show local_file.pet

# تصفية حسب نوع المورد
tofu state list aws_s3_bucket.cerberus-finance

✏️ إعادة تسمية مورد

# إعادة تسمية مورد في الحالة
tofu state mv random_pet.super_pet_1 random_pet.ultra_pet

# ملاحظة: يجب أيضاً إعادة تسمية المورد في ملف الإعداد

⚠️ تنبيه مهم

عند استخدام tofu state mv، يجب أيضاً تحديث اسم المورد في ملف الإعداد (.tf). وإلا سيقوم tofu apply بحذف المورد وإعادة إنشائه!

🗑️ إزالة مورد من الحالة

# إزالة مورد من إدارة OpenTofu (لا يحذفه فعلياً)
tofu state rm local_file.hall_of_fame

💡 متى تستخدم tofu state rm؟

عندما تريد التوقف عن إدارة مورد معين عبر OpenTofu، لكنك تريد الاحتفاظ به فعلياً. مثال: نقل إدارة مورد إلى فريق آخر أو أداة أخرى.

⚡ أوامر إضافية مفيدة

الأمر الوظيفة متى تستخدمه
tofu validate التحقق من صحة الـ syntax قبل أي أمر آخر
tofu fmt تنسيق الكود بشكل قياسي قبل رفع الكود إلى GitHub
tofu show عرض الحالة الحالية بعد apply لفحص النتائج
tofu show -json عرض الحالة بصيغة JSON للمعالجة البرمجية
tofu providers عرض الـ Providers المستخدمة لفحص الإعدادات
tofu graph رسم بياني للاعتماديات لفهم العلاقات بين الموارد
tofu console وحدة تحكم تفاعلية لاختبار الدوال والتعابير

💡 نصيحة للمقابلات

ما الفرق بين tofu validate و tofu plan؟
• validate: يتحقق من صحة الـ syntax فقط (لا يتصل بالـ Provider)
• plan: يتحقق من القيم ويولد خطة تنفيذ (يتصل بالـ Provider)

☁️ الحالة البعيدة (Remote State)

في بيئات العمل الحقيقية، يجب تخزين الحالة في مكان مشترك وآمن، وليس محلياً.

📄 إعداد S3 كـ Backend

terraform {
  backend "s3" {
    bucket         = "my-opentofu-state-bucket"
    key            = "project/terraform.tfstate"
    region         = "us-west-1"
    dynamodb_table = "state-locking"  # ← قفل الحالة
  }
}

✅ مميزات الـ Remote State

  • التعاون: فريق كامل يمكنه العمل على نفس البنية التحتية
  • الأمان: تشفير أثناء التخزين والنقل
  • قفل الحالة: منع التعديلات المتزامنة
  • النسخ الاحتياطي: حماية من الفقدان

⚠️ خطوات الانتقال إلى Remote State

  1. أضف الـ backend block في terraform.tf
  2. شغل tofu init (سيطلب نسخ الحالة الحالية)
  3. وافق على النسخ بكتابة yes
  4. احذف ملف الحالة المحلي (أصبح غير ضروري)

⚠️ أخطاء شائعة يجب تجنبها

❌ خطأ 1: تحرير ملف الحالة يدوياً

لا تحرر terraform.tfstate يدوياً أبداً! استخدم الأوامر المخصصة: tofu state mv, tofu state rm, إلخ.

❌ خطأ 2: وضع ملف الحالة في Git

ملف الحالة يحتوي معلومات حساسة. أضفه إلى .gitignore واستخدم Remote Backend. 

# .gitignore
*.tfstate
*.tfstate.*
.terraform/

❌ خطأ 3: نسيان تحديث ملف الإعداد بعد state mv

عند إعادة تسمية مورد في الحالة، يجب أيضاً تحديث الاسم في ملف .tf. وإلا سيقوم OpenTofu بحذف المورد وإعادة إنشائه!

❌ خطأ 4: استخدام tofu state push بدون حذر

هذا الأمر يمكن أن يدمر الحالة البعيدة. استخدمه فقط في حالات الطوارئ، ويفضل مع --force فقط إذا كنت متأكداً تماماً.

🎤 أسئلة مقابلات مهمة

سؤال 1: ما هو ملف الحالة ولماذا هو مهم؟

ملف الحالة (terraform.tfstate) هو مصدر الحقيقة لـ OpenTofu. يحتوي على جميع تفاصيل البنية التحتية المُنشأة، ويستخدم لمقارنة الحالة الحالية مع الإعدادات المطلوبة لتحديد ما يجب إنشاؤه أو تحديثه أو حذفه.

سؤال 2: ما الفرق بين create_before_destroy والسلوك الافتراضي؟

السلوك الافتراضي: يحذف المورد القديم أولاً، ثم ينشئ الجديد.
create_before_destroy: ينشئ الجديد أولاً، ثم يحذف القديم.
مفيد للـ Zero Downtime في بيئات الإنتاج.

سؤال 3: هل يمكن تعطيل الحالة؟

لا! الحالة إلزامية ولا يمكن تعطيلها. يمكن فقط تعطيل تحديث الحالة عبر -refresh=false، لكن هذا غير مستحسن لأنه قد يؤدي إلى عدم اتساق.

سؤال 4: ما الفرق بين tofu state rm و tofu destroy؟

tofu state rm: يزيل المورد من إدارة OpenTofu فقط (لا يحذفه فعلياً).
tofu destroy: يحذف المورد فعلياً من البنية التحتية.

سؤال 5: لماذا يجب استخدام Remote Backend؟

لأن الحالة تحتوي معلومات حساسة، ويجب: • تخزينها في مكان آمن ومشفر • السماح لفريق كامل بالعمل عليها • تفعيل قفل الحالة لمنع التعديلات المتزامنة • عدم وضعها في Git

⚡ مرجع سريع

# دورة العمل مع الحالة
tofu init          # تهيئة (ينشئ الحالة عند أول apply)
tofu plan          # يعرض الخطة (يحدث الحالة)
tofu apply         # ينفذ ويحدث الحالة
tofu show          # يعرض الحالة
tofu destroy       # يحذف ويحدث الحالة

# أوامر الحالة
tofu state list    # عرض الموارد
tofu state show    # عرض مورد محدد
tofu state mv      # إعادة تسمية/نقل
tofu state rm      # إزالة من الإدارة

# قواعد دورة الحياة
lifecycle {
  create_before_destroy = true   # إنشاء الجديد أولاً
  prevent_destroy       = true   # منع الحذف
  ignore_changes        = [ tags ]  # تجاهل تغييرات
}
