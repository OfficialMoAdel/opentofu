🔧 OpenTofu - Provisioners & Workspaces

مرجع شامل لأدوات التهيئة (Provisioners) ومساحات العمل (Workspaces)

📋 نظرة عامة (Overview)

الـ Provisioners تتيح تشغيل أوامر على الموارد البعيدة أو المحلية. الـ Workspaces تتيح استخدام نفس الإعدادات لبيئات متعددة (dev, staging, prod).

remote-exec

تشغيل أوامر على المورد البعيد

local-exec

تشغيل أوامر على الجهاز المحلي

connection

إعدادات الاتصال (SSH, WinRM)

workspaces

بيئات متعددة بنفس الإعدادات

🔧 أساسيات الـ Provisioners

الـ Provisioners تُستخدم لتشغيل أوامر أو سكربتات بعد إنشاء المورد. تُضاف داخل الـ resource block.

⚠️ قاعدة ذهبية

استخدم الـ Provisioners كـ خيار أخير فقط! يفضل دائماً استخدام الخيارات الأصلية للمورد:

الـ Provider المورد الخيار البديل
AWS aws_instance user_data
Azure azurerm_virtual_machine custom_data
GCP google_compute_instance metadata

📄 مثال: استخدام user_data (الطريقة المفضلة)

resource "aws_instance" "webserver" {
  ami           = "ami-0edab43b6fa892279"
  instance_type = "t2.micro"

  # ✅ الطريقة المفضلة: user_data
  user_data = <<-EOF
    #!/bin/bash
    sudo apt update
    sudo apt install nginx -y
    systemctl enable nginx
    systemctl start nginx
    EOF
}

🌐 remote-exec Provisioner

يُستخدم لتشغيل أوامر على المورد البعيد (مثل خادم ويب) بعد إنشائه.

📄 مثال عملي كامل

resource "aws_instance" "webserver" {
  ami           = "ami-0edab43b6fa892279"
  instance_type = "t2.micro"
  key_name      = aws_key_pair.web.id
  vpc_security_group_ids = [ aws_security_group.ssh-access.id ]

  # ← remote-exec provisioner
  provisioner "remote-exec" {
    inline = [
      "sudo apt update",
      "sudo apt install nginx -y",
      "sudo systemctl enable nginx",
      "sudo systemctl start nginx",
    ]
  }

  # ← connection block (مطلوب)
  connection {
    type        = "ssh"
    host        = self.public_ip  # ← self يشير للمورد الحالي
    user        = "ubuntu"
    private_key = file("/root/.ssh/web")
  }
}

resource "aws_key_pair" "web" {
  # إعدادات المفتاح
}

resource "aws_security_group" "ssh-access" {
  # إعدادات الـ Security Group للسماح بـ SSH
}

💡 متطلبات remote-exec

  • اتصال شبكة: SSH للـ Linux، WinRM للـ Windows
  • Security Group: يسمح بالاتصال
  • مفتاح: SSH Key Pair أو WinRM credentials
  • connection block: يحدد كيفية الاتصال

✅ ما هو self؟

self هو تعبير خاص داخل الـ resource block يشير إلى المورد الحالي. self.public_ip يعني "الـ IP العام لهذا المورد".

💻 local-exec Provisioner

يُستخدم لتشغيل أوامر على الجهاز المحلي (حيث يعمل OpenTofu)، وليس على المورد البعيد.

📄 مثال: حفظ معلومات في ملف محلي

resource "aws_instance" "webserver" {
  ami           = "ami-0edab43b6fa892279"
  instance_type = "t2.micro"

  # ← local-exec provisioner (لا يحتاج connection)
  provisioner "local-exec" {
    command = "echo ${aws_instance.webserver2.public_ip} >> /tmp/ips.txt"
  }
}

💡 الفرق بين remote-exec و local-exec

المعيار remote-exec local-exec
أين يعمل؟ على المورد البعيد على الجهاز المحلي
connection block ✅ مطلوب ❌ غير مطلوب
الاستخدام تثبيت برامج على الخادم تسجيل معلومات، تشغيل سكربتات محلية

⏱️ Create-Time vs Destroy-Time

الـ Provisioners تعمل بعد إنشاء المورد افتراضياً (create-time). يمكن جعلها تعمل قبل الحذف (destroy-time).

📄 مثال: provisioner يعمل عند الحذف

resource "aws_instance" "webserver" {
  ami           = "ami-0edab43b6fa892279"
  instance_type = "t2.micro"

  # ← create-time (الافتراضي)
  provisioner "local-exec" {
    command = "echo Instance Created! >> /tmp/state.txt"
  }

  # ← destroy-time
  provisioner "local-exec" {
    when    = destroy  # ← يعمل قبل الحذف
    command = "echo Instance Destroyed! >> /tmp/state.txt"
  }
}

📄 مثال: التعامل مع الفشل

# السلوك الافتراضي: فشل الـ provisioner = فشل الـ apply
provisioner "local-exec" {
  on_failure = fail  # ← الافتراضي
  command    = "some-command"
}

# الاستمرار حتى لو فشل الـ provisioner
provisioner "local-exec" {
  on_failure = continue  # ← الاستمرار
  command    = "some-command"
}

⚠️ التلوث (Tainting)

إذا فشل الـ provisioner، يتم تعليم المورد كـ tainted. في الـ apply التالي، سيتم إعادة إنشاء المورد بالكامل!

📁 مساحات العمل (Workspaces) - الأساسيات

الـ Workspaces تتيح استخدام نفس الإعدادات لبيئات متعددة (development, production) مع قيم مختلفة.

🔧 الأوامر الأساسية

# عرض جميع الـ workspaces
tofu workspace list
# النتيجة:
# * default

# إنشاء workspace جديد
tofu workspace new production
tofu workspace new development

# التبديل إلى workspace
tofu workspace select production

💡 ملاحظة مهمة

عند إنشاء workspace جديد، يتم التبديل إليه تلقائياً. النجمة * تشير إلى الـ workspace الحالي.

📂 هيكل الملفات مع الـ Workspaces

project/ ├── main.tf ├── provider.tf ├── variables.tf └── terraform.tfstate.d/ ← مجلد خاص بالـ workspaces ├── development/ │ └── terraform.tfstate └── production/ └── terraform.tfstate

ℹ️ ماذا يحدث مع الـ State؟

عند استخدام الـ Workspaces، لا يتم إنشاء ملف terraform.tfstate في المجلد الرئيسي. بدلاً من ذلك، يتم إنشاء مجلد terraform.tfstate.d يحتوي على مجلد لكل workspace.

🎯 استخدام الـ Workspaces عملياً

📄 مثال: instance_type مختلف لكل بيئة

# variables.tf
variable "instance_type" {
  type = map
  default = {
    "development" = "t2.micro"
    "production"  = "m5.large"
  }
}

# main.tf
resource "aws_instance" "webserver" {
  ami           = var.ami
  instance_type = lookup(var.instance_type, terraform.workspace)
  #                                        ↑                    ↑
  #                                        الخريطة           الـ workspace الحالي

  tags = {
    Environment = terraform.workspace  # ← اسم الـ بيئة
  }
}

🔍 اختبار في الـ Console

# في workspace development
tofu console
> terraform.workspace
"development"
> lookup(var.instance_type, terraform.workspace)
"t2.micro"

# بعد التبديل إلى production
tofu workspace select production
> terraform.workspace
"production"
> lookup(var.instance_type, terraform.workspace)
"m5.large"

✅ النتيجة

  • development workspace: t2.micro + tag "development"
  • production workspace: m5.large + tag "production"
  • نفس الكود، قيم مختلفة حسب الـ بيئة!

🎯 مثال عملي كامل: نشر التطبيق في بيئات متعددة

📄 main.tf

module "payroll_app" {
  source     = "/root/opentofu-projects/modules/payroll-app"
  app_region = lookup(var.region, terraform.workspace)
  ami        = lookup(var.ami, terraform.workspace)
}

📄 variables.tf

variable "region" {
  type = map
  default = {
    "us-payroll"    = "us-east-1"
    "uk-payroll"    = "eu-west-2"
    "india-payroll" = "ap-south-1"
  }
}

variable "ami" {
  type = map
  default = {
    "us-payroll"    = "ami-24e140119877avm"
    "uk-payroll"    = "ami-35e140119877avm"
    "india-payroll" = "ami-55140119877avm"
  }
}

# نشر في كل بيئة
tofu workspace select us-payroll

tofu workspace select uk-payroll

tofu workspace select india-payroll
tofu apply

⚠️ أخطاء شائعة يجب تجنبها

❌ خطأ 1: الإفراط في استخدام الـ Provisioners

استخدم user_data أو custom_data بدلاً من الـ Provisioners عندما يكون ذلك ممكناً. الـ Provisioners تسبب مشاكل في الـ state وتحتاج إلى اتصال شبكة.

❌ خطأ 2: نسيان الـ connection block مع remote-exec

# ❌ خطأ - remote-exec بدون connection لن يعمل
provisioner "remote-exec" {
  inline = ["echo hello"]
}

# ✅ صحيح
provisioner "remote-exec" {
  inline = ["echo hello"]
}
connection {
  type = "ssh"
  # ...
}

❌ خطأ 3: نسيان أن الـ workspace يتغير تلقائياً

عند إنشاء workspace جديد بـ tofu workspace new، يتم التبديل إليه تلقائياً. تأكد دائماً من أنك في الـ workspace الصحيح باستخدام tofu workspace list.

❌ خطأ 4: خلط الـ Workspaces مع الـ Remote State

عند استخدام Remote State (مثل S3)، قد تتصرف الـ Workspaces بشكل مختلف. اقرأ الوثائق بعناية قبل الجمع بينهما.

🎤 أسئلة مقابلات مهمة

سؤال 1: ما الفرق بين remote-exec و local-exec؟

remote-exec: يشغل أوامر على المورد البعيد، يحتاج إلى connection block.
local-exec: يشغل أوامر على الجهاز المحلي، لا يحتاج إلى connection.

سؤال 2: لماذا لا يُنصح باستخدام الـ Provisioners؟

لأنها تعتمد على اتصال شبكة، قد تفشل وتسبب tainting للمورد، ولا يتم تتبعها في الـ state بشكل صحيح. يفضل استخدام الخيارات الأصلية مثل user_data.

سؤال 3: ما هو الـ Tainting؟

عندما يفشل provisioner أو أي خطوة أثناء إنشاء المورد، يتم تعليم المورد كـ tainted. في الـ apply التالي، سيتم إعادة إنشاء المورد بالكامل. يمكن إلغاء الـ taint باستخدام tofu untaint.

سؤال 4: ما هي الـ Workspaces ولماذا نستخدمها؟

الـ Workspaces تتيح استخدام نفس الإعدادات لبيئات متعددة (dev, staging, prod) مع قيم مختلفة لكل بيئة. كل workspace له ملف state خاص به في مجلد terraform.tfstate.d.

سؤال 5: كيف تحصل على اسم الـ workspace الحالي؟

باستخدام التعبير terraform.workspace. يمكن استخدامه مع دالة lookup() لاختيار قيم مختلفة حسب البيئة.

# ═══════════════════════════════════════════════
# Provisioners
# ═══════════════════════════════════════════════

# remote-exec (على المورد البعيد)
provisioner "remote-exec" {
  inline = ["command1", "command2"]
}
connection {
  type        = "ssh"
  host        = self.public_ip
  user        = "ubuntu"
  private_key = file("/path/to/key")
}

# local-exec (على الجهاز المحلي)
provisioner "local-exec" {
  command = "echo hello >> file.txt"
}

# destroy-time
provisioner "local-exec" {
  when    = destroy
  command = "cleanup"
}

# ═══════════════════════════════════════════════
# Workspaces
# ═══════════════════════════════════════════════

tofu workspace list       # عرض
tofu workspace new name  # إنشاء
tofu workspace select name  # تبديل

# في الكود
terraform.workspace  # اسم الـ workspace الحالي
lookup(var.map, terraform.workspace)  # اختيار قيمة
